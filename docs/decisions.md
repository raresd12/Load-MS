# Product decisions after the handoff

Numbers refer to `LOAD_MS_CLAUDE_HANDOFF.md` section 19.4 where applicable.
Taken 2026-09-18 by the owner's delegation ("go with the recommended defaults; we adjust after").

| # | Decision | Rule |
|---|---|---|
| 19.4-1 | Program duplication | Fresh copy. Targets, warm-up and metadata are copied; progression records are re-initialised from targets with no recommendation note, no `sourceSessionId`, no `sourcePlanGeneratedAt`. Sessions are never copied. |
| 19.4-2 | Prescription precedence | One shared resolver used by Workouts and Workout Log: (1) stored progression earned from a saved session of this program, (2) generated plan for the day, (3) program target, (4) baseline. Each resolved value carries a `source` label. Editing a program target deletes the stored progression and the pending plan entry for that programExerciseId, so the next session starts from the new target. |
| 19.4-3 | Rest ranges in the timer | A range `[min, max]` starts the timer at `max`. The timer offers a one-tap "min" shortcut (e.g. 2:30) when a range exists. Stored ranges are never rewritten. The program editor shows and preserves the range as `min-max`. |
| new-A | Working weight | The heaviest logged set weight (top set), not the mean. Comparison with previous sessions uses top set as well. |
| new-B | History recency | Sessions older than 42 days do not count as fresh history. If the most recent qualifying session is older than 42 days the engine returns `hold` with a "long break" reason and `conservative: true`; confidence is at most `medium`. |
| new-C | Skipped exercise | An exercise with zero sets that have numeric reps is `insufficient_data` for that session and is excluded from history samples. |
| new-D | First bad session | With no usable history, a below-target/high-RPE session yields `hold`, never `reduce_load`. Reduction needs two consecutive qualifying bad sessions. Pain handling stays independent. |
| new-E | Session edit/delete | History allows editing set reps/kg/RPE, session RPE and notes, and deleting a session (with confirmation). After either, the next plan and progression for that day are regenerated from the most recent remaining session of that program+day (or cleared if none). |
| new-F | Program archive | Programs can be archived/unarchived. Active and default programs cannot be archived. Archived programs are hidden by default and keep their data. |
| new-G | Corrupt storage | A key whose JSON fails to parse is copied to `<key>.corrupt-<n>` before any fallback is used, the fallback is not written back automatically, and the UI shows a persistent warning with the key name. |

| new-H | Session edit normalisation | The History editor rebuilds a session with the same day-driven normalisation as the save path, so an exercise that is no longer in the program day is dropped from the edited session. Delete never drops anything. |

| # | Decision | Rule |
|---|---|---|
| new-M | Top set and failed attempts | Only sets with at least one completed rep are top-set candidates (new-A). A logged `130 kg x 0` never becomes the working weight or the load the next session is compared against; when no set has reps the planned weight is used. |

Reset (the explicit "wipe everything" action) also removes the `<key>.corrupt-<n>` copies and clears their in-memory issues. Re-reading an identical corrupt key never re-notifies the UI. |
| new-Q | History delete atomicity | When the last session of a program + day is deleted, the day's progressions are removed in the same `persistWorkoutSave` batch as the sessions (`deleteProgressionsForDayId`); nothing is committed on failure. |

| new-T | Refilled plan entries | A base-plan entry inside a "generated" day plan (refilled after a target edit removed it) resolves as `target`, not `plan`; a `manual` plan and entries flagged `manuallyAdjusted` still count as plan values. |

## Clarifications recorded during the H1 fix round 2 (2026-09-23)

| # | Decision | Rule |
|---|---|---|
| new-U | Corrupt keys and writers | new-G also protects the write path: `writeStorage` / `writeStorageBatch` refuse (code `corrupt`, nothing written, no partial batch) any key whose stored text is not valid JSON, unless the caller passes `overwriteCorrupt` for an explicit user action. Every program-storage writer, `persistWorkoutSave` and the `useLocalStorageState` write therefore fail instead of writing a value computed from the empty fallback over the user's data, and the read-corrupt warning stays truthful ("nothing was overwritten"). The warning offers "Discard unreadable data" (`discardCorruptStorageValue`): the raw text must already sit in a `<key>.corrupt-<n>` copy, then the key is removed, the issue cleared and the defaults re-seeded. A knowing overwrite clears the read-corrupt issue. |
| new-V | Share library references | `validateProgramShareStrict` rejects a program exercise whose `exerciseId` resolves to no Library entry in the share, the local Library or the built-in config, instead of importing a placeholder "Exercise" with no technique content. App-exported shares always carry their referenced entries, so they still round-trip; H2's match/remap editor builds on this rule. |
| new-R (extended) | Target edit validation | `updateProgramExerciseTargetChecked` applies the strict share rules to every field a patch touches (RPE 1-10 in .5 steps, positive reps with min <= max or a label, weight empty / >= 0 / "BW", sets 1-30) and returns `{ ok:false, errors }`; an unusable rest input still keeps the current value (19.4-2). |
| new-W | Seeding | `seedDefaultProgramIfNeeded` computes every seed collection in memory and writes the changed keys in one `writeStorageBatch`: a failed fresh install leaves nothing behind and seeds fully on the next run; a default program that exists but lost days / sections / exercises / baselines / state gets the missing records back (add-only by id, progressions of an existing program untouched); a healthy mount writes nothing. |
| new-E (completed) | Program state after history changes | After a session delete or edit, `ProgramState` (`lastCompletedDayId`, `nextRecommendedDayId`, `lastWorkoutDate`) is derived from the most recent remaining session of that program (`deriveProgramStatePatchFromSessions`) in the same `persistWorkoutSave` batch, or reset to "nothing completed, first day next" when none remains. Legacy sessions without a `programId` never drive it. |
| new-X | Checked program writers | `setActiveProgramChecked` / `updateProgramMetadataChecked` return `{ ok, error, code }`; the legacy wrappers return `null` on a failed write. The Program card only switches the day selection / closes the details editor after the write succeeded and shows the error otherwise. |

## Decisions recorded during H2 implementation (2026-09-26)

| # | Decision | Rule |
|---|---|---|
| H2-1 | Program draft writers | A `ProgramDraft` (`src/lib/programDraft.js`) is in-memory only; nothing reaches program keys before `saveProgramDraft` / `applyProgramDraft` (`src/lib/programStorage.js`), both validated first (`validateProgramDraft`), refused while any program key is unreadable (new-U) and written in one `writeStorageBatch`. `saveProgramDraft` creates a NEW inactive custom program (`isDefault: false`, `isArchived: false`, fresh `ProgramState`, no baseline / progression rows - targets are the fallback, like a share import), adds proposed Library entries add-only and never overwrites an existing entry. `applyProgramDraft` edits the EXISTING custom program named by `draft.sourceProgramId` (defaults refused): exercises whose draft id equals a stored `programExerciseId` keep that id and baseline, added ones get ids in the program namespace, removed ones lose their baseline and progression rows; an exercise whose prescription changed (library id, sets, reps, weight, RPE, rest, loadType, weightMode) loses its stored progression per 19.4-2, notes / type / optional edits keep it; days, sections and `orderIndex` are rebuilt (surviving day / section ids kept); program id, `createdAt`, `isArchived` and `ProgramState` are kept, except that `lastCompletedDayId` / `nextRecommendedDayId` pointing at a removed day become `null` / the first day. Workout sessions are never touched. `nextPlans` live in App state, so the writer returns `removedProgramExerciseIds` and `changedProgramExerciseIds` and the UI runs `removeExerciseFromNextPlans` for each. |
| H2-2 | Measurement profile (answers 19.4-4 for now) | A ProgramExercise may persist `loadType` (`external` / `bodyweight` / `optionalExternal`) and `weightMode` (`kg` / `per dumbbell` / `additional load`); the draft writers always persist them. `resolveProgramExerciseLoadProfile` prefers the persisted values and otherwise derives them exactly as before H2 (built-in config, then Library equipment `bodyweight`, then `external` / `kg`), so legacy and default programs keep identical view models. Measurement = `loadType` + `weightMode` + `targetReps.label`; true time / distance logging stays H5. `exportProgramShare` carries the fields, `validateProgramShareStrict` accepts only the enums, requires `sourceWeight` to be text and ignores unknown envelope fields such as `draftMeta` (draft provenance), as does `importProgramShare`. |
| H2-3 | Saved drafts (19.4-8) | Optional drafts live under `rpe-tracker.program-drafts.v1` (`STORAGE_KEYS.programDrafts`, so backup / reset track it): at most 5 entries `{ draftId, origin, sourceProgramId, updatedAt, draft }`, newest first, upserted by `draftId`, oldest dropped beyond the cap, at most 256 KB each. A stored draft is the whitelist-normalised draft (`normalizeProgramDraft`): raw uploads, image data, pasted source text and the Gemini key are never part of it, whatever a component attached to the object. Extracted source content is retained only in component memory for the request (13.4), never in this key. |
| H2-4 | Source-listed weights (19.4-9) | A load written in a source ("80 kg", "70% 1RM", "BW +10 kg") is kept as `sourceWeight` reference text on the draft exercise, the ProgramExercise and the day view model. It never becomes `targetWeight`, a baseline, a progression value or an earned recommendation; the deterministic engine keeps computing loads from logged sessions and targets. Editing `sourceWeight` does not touch `targetWeight`. |

## Decisions recorded during the H2 fix round 1 (2026-09-26)

| # | Decision | Rule |
|---|---|---|
| H2-5 | Library remap = new occurrence | Progression identity is per occurrence of ONE Library exercise. In `applyProgramDraft` a draft exercise keeps its stored `programExerciseId` (baseline, progression, logged history) only while its `exerciseId` is unchanged; a Library remap (Studio picker, or an AI edit that returns a kept `refId` with a different `exerciseId`) is a remove + add: the old occurrence's baseline and progression rows go, its sessions stay attached to the retired id, the new occurrence gets a new id and starts from its targets. `diffDraftAgainstProgram` reports it as removed + added (`added[].replaces`). This supersedes the "library id" item of H2-1's changed-prescription list. In the AI edit converter the link is dropped in code (not only by prompt): no load, prescription or optional flag is carried onto the different exercise, the old one is listed under `removed`, and the swap is disclosed in `uncertainty`. |
| H2-6 | Retired ids | A new program exercise / day id minted by `applyProgramDraft` is never one that a workout session, workout draft, baseline, progression, program state or next-plan entry still references, whatever the current records hold (`getReferencedRecordIds`): a removed occurrence's history can never re-attach to a later addition at the same ordinal. Unreferenced ids stay deterministic and may be reused. |
| H2-7 | Derived reps label | `targetReps.label` that only repeats the numeric range ("8-12" on 8-12, "10" on 10-10) equals no label for `diffDraftAgainstProgram` and `applyProgramDraft` (`comparableTargetReps`), and the AI edit converter keeps a kept exercise's stored label as it is (including none) on a verbatim echo. An unchanged AI echo of a Studio-created program (label `null`) therefore resets nothing. |
| H2-8 | Studio session and review drafts | The Studio's working copy is reported to App state on every edit (`onDraftChange`) and restored on remount (a bottom-nav tab switch unmounts the Program page), with `initialDraft` as the dirty / diff baseline; a pending autosave is flushed on unmount. A review draft (AI import, AI edit, file import) is stored under `rpe-tracker.program-drafts.v1` as soon as it opens, before any edit, and its AI notes travel with it (`draft.reviewNotes`: `changes`, `removed`, `uncertainty` text lists, whitelist-normalised) so a resumed review shows them. Cancel on a review or resumed draft, and "Discard" on a Resume card, ask for confirmation. |
| H2-9 | AI edit fidelity checks in code | Edit mode emits `draftMeta.sectionIds` (share section -> stored section by name on a kept day) so kept sections keep their ids and nothing shows as "moved"; a base section without exercises (a rest day's "Recovery") is carried over as an empty section. A kept day's warm-up that equals the stored one keeps the stored object (item ids included); one that differs is disclosed in `uncertainty`, and `diffDraftAgainstProgram` lists day-level changes (`days.changed`: focus, notes, isOptional, warm-up text) so the review panel shows them. The "Edit with AI" help text only suggests edits the response schema can express (no day/exercise `isOptional`). |
| H2-10 | Library text in prompts, delimiter spacing | The exercise catalog inside the rules text is data: every field is forced onto one line (whitespace collapsed, zero-width characters dropped), capped, "|" replaced and delimiter phrases neutralised, and the prompt states that catalog lines are data. AI-extracted exercise names are single-line. `neutralizeDelimiters` strips zero-width characters and matches any spacing (`[\s_-]*`) between the words of a delimiter phrase, so "PROGRAM  DATA END" cannot pass as a delimiter. |
| H2-11 | Unusable rest / weight text in the Studio | Rest or weight text the editor cannot parse ("150-", "abc") reaches the draft as typed (`updateExercise` keeps the string), so `validateProgramDraft` reports it, Save stays disabled and the reopened field shows the text; a stored draft (`saveDraftToStorage` / `loadStoredDraft`) keeps that text as typed too, so a resumed draft still fails validation for rest AND weight (fix round 2: `null` would have passed as "coach decides" and Apply would have cleared the stored target and its progression from a typo). The draft never keeps a previous value behind a field that shows something else. `applyProgramDraft` checks the corrupt-key guard before the program lookup so an unreadable programs key reports `corrupt`, not `not-found`. |
